# AI 사용 기록

AI는 개념 질문과 직접 작성한 코드의 디버깅에만 사용할 수 있습니다. 사용하지 않았다면 아래에 `사용하지 않음`이라고 적습니다. 사용량을 늘릴 필요는 없습니다.

| 허용되는 도움 | 예시 |
|---|---|
| 개념 이해 | HTTP 404와 422의 차이, await의 의미를 다른 예시로 설명해 달라고 질문 |
| 자신의 코드 디버깅 | 직접 작성한 짧은 함수와 오류를 보여 주고 원인과 확인 방법을 질문 |

과제 전체 풀이, TODO의 완성 코드, 참고 답안을 요청하지 않습니다. 디버깅 답변도 이해한 원인과 수정 내용을 자신의 말로 기록하고 다시 실행합니다. API 키, `.env`와 인증 헤더를 질문에 포함하지 않습니다.

## 사용 여부

- 사용 여부: 사용함 (개념 질문, 직접 작성한 코드의 디버깅)
- 사용한 도구: Claude

## 도움 기록

도움을 받은 건마다 표의 행을 추가합니다. 대화 전문보다 질문과 직접 확인한 결과를 구체적으로 적습니다.

| 단계/함수 | 직접 시도한 내용과 문제 | 질문 요약 | 받은 설명 | 내가 수정하거나 확인한 내용 | 재실행 결과 |
|---|---|---|---|---|---|
| 자료 수집 `collect_releases` | HTTP 요청이 실패했을 때 예외 처리가 어떻게 이루어지는지 헷갈림 | `raise_for_status()`의 역할 | HTTP 오류 상태 코드에서 예외를 발생시키고, `except`에서 실패 기록과 중단을 처리할 수 있음 | 요청 실행과 성공은 다르다는 점을 이해하고 상태 검사 빈칸 작성 | `check collect` 통과 |
| 문서 정제 `normalize_releases` | 같은 ID가 여러 번 나올 때 어느 시점에 중복으로 볼지 헷갈림 | 중복 ID 판단 기준 | 이미 정상 채택한 ID를 기준으로 판단해야 하며, 먼저 나온 불량 데이터 때문에 뒤의 정상 데이터를 막으면 안 됨 | `accepted_ids` 기준으로 중복 조건 작성 | `check documents` 통과 |
| 문서 API Pydantic 모델 | 일반 검증과 엄격한 검증의 차이를 몰랐음 | `strict=True`의 의미 | 엄격한 검증은 `"false"`나 `1`을 boolean으로 자동 변환하지 않고 거부하며, API 검증 단계에서 422로 처리됨 | `Document`, `QueryRequest`, `QueryReply` 필드 작성 후 자료형이 다른 입력이 거부되는지 확인 | `check document-api` 통과 |
| 실패 처리 `query_with_retry` | 공급자가 429를 주면 우리 API도 429를 줘야 하는지 헷갈림 | 공급자 429와 API 응답 503 | 공급자 429는 그쪽 요청 제한이고, 우리 서비스에서는 처리 불가 상황인 503으로 바꿔 우리 서버의 429와 구분할 수 있음 | 공급자 429를 503으로 변환하는 분기 작성 | `check retry` 통과 |
| 요청 제한 `admit_query` | 요청 제한을 어느 단계에서 적용하고 고정 구간이 어떻게 동작하는지 헷갈림 | 요청 제한 위치와 고정 구간 방식 | 요청 형식과 문서 ID 검증 뒤, 모델 호출 전에 적용. 고정 구간은 구간이 끝나면 횟수를 초기화 | 구간 갱신, 한도 확인, 요청 수 증가 조건 작성 | `check observe` 통과. 직접 확인: 30회 허용, 31번째 429, `Retry-After: 60` |
